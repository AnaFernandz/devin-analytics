At a glance

Testing a generative AI feature means testing the whole system — model, prompts, retrieved data, tools, guardrails, and UI — against behaviors that are probabilistic. Replace "does it return the expected string?" with "does it reliably meet a measurable quality bar, and does it fail safely when it doesn't?"

The QA lifecycle

Treat these as a loop: every production incident becomes a new test case in phase 2.

01

Define scope, intended use, and risk

Before any testing

Map the system boundary: model and version, system prompt, retrieval sources, tools and their permissions, guardrails, and UI. Write down who the users are, what the feature must do, what it must never do, and how bad each failure would be.

Inputs
Product requirements, user personas, data sources, tool list
Outputs
Risk register with severity, testable requirements, out-of-scope list
Exit criteria
Every high-severity risk has an owner, a control, and a planned test
Turning vague requirements into testable ones

"The assistant should be accurate" is not testable. "For in-scope billing questions, answers must match the current policy document, cite it, and say 'I don't know' when the policy does not cover the question; ≥ 95% of the golden set passes, with no fabricated policy" is testable. Each requirement needs a population, a measurable property, and a threshold.

02

Build a versioned evaluation dataset

Core asset

Collect real and realistic inputs, then tag each case by intent, risk, language, persona, and difficulty so results can be sliced. Store the dataset in version control next to the prompts.

Smoke set
20–50 fast, stable cases run on every change
Golden / regression set
Core journeys plus every past bug, with reference answers
Adversarial set
Jailbreaks, injections, PII probes, off-topic and abusive inputs
Edge-case set
Ambiguous, multi-turn, long-context, multilingual, typos, empty input
Holdout set
Never used to tune prompts — guards against overfitting
03

Choose metrics, graders, and thresholds

Before seeing results

Pick the quality dimensions that matter for this feature, decide how each is measured, and set thresholds before you run the suite, so results cannot quietly move the goalposts. Validate any LLM-as-judge grader against human labels first.

Outputs
Metric definitions, grader prompts (versioned), thresholds per slice
Exit criteria
Grader agrees with human reviewers on a labeled sample at an agreed rate
04

Execute functional, adversarial, and non-functional tests

Every change

Combine conventional tests (unit tests for prompt assembly, contract tests for tool schemas, E2E journeys) with evaluation runs against the dataset. Add red-teaming, load and latency tests, and fault injection such as provider timeouts, malformed model output, and empty retrieval.

Outputs
Eval report per run: scores by slice, failures with traces, cost and latency
Exit criteria
All defined suites executed on the release candidate configuration
05

Gate the release

Go / no-go

Compare the candidate to the current production baseline on the same dataset. Block on any critical safety or security failure regardless of averages. Roll out gradually behind a flag with a tested rollback and a kill switch.

Outputs
Signed-off release checklist, known-limitations list, rollback plan
Exit criteria
All gates in the release checklist pass or have an approved, time-boxed exception
06

Monitor in production and feed back

Continuous

Sample live traffic (with privacy controls), run online evaluations, watch user feedback and operational metrics, and convert every confirmed failure into a regression case.

Outputs
Dashboards, alerts, triaged incident log, new dataset cases
Loops back to
Phase 2 — the dataset grows with every incident

Testing by system type

Chat and prompt-based features

  • Prompt assembly: unit-test that system prompt, user input, history, and variables are combined correctly and escaped.
  • Multi-turn context: follow-ups ("what about the second one?"), topic switches, corrections, and very long conversations.
  • Persona and tone: consistent voice, no unwanted claims of being human, correct language for the locale.
  • Scope control: off-topic requests are declined politely and redirected.
  • Structured output: JSON/markdown validates against the schema on every run; the app handles malformed output.
  • Robustness: typos, slang, mixed languages, emoji, empty input, extremely long input.
  • Metamorphic tests: paraphrases of the same question should yield consistent answers.

Retrieval-augmented generation (RAG)

Test retrieval and generation separately — a perfect generator cannot fix missing context.

  • Retrieval quality: recall@k and precision of retrieved chunks against labeled relevant documents.
  • Faithfulness: every claim in the answer is supported by retrieved text; nothing comes from model memory when it shouldn't.
  • Citations: cited sources exist, are relevant, and actually support the sentence they are attached to.
  • Abstention: when the answer is not in the corpus, the system says so instead of guessing.
  • Freshness: updated or deleted documents are reflected after re-indexing; stale versions are not cited.
  • Access control: users only retrieve documents they are permitted to see (test with multiple roles and tenants).
  • Indirect injection: plant instructions inside documents ("ignore previous instructions…") and confirm they are not followed.
  • Conflicting sources: the system surfaces or resolves contradictions rather than picking one silently.

Agents and tool-using systems

Evaluate the whole trajectory — which tools were called, with what arguments, in what order — not just the final message.

  • Tool selection: the right tool is chosen; no tool is called when none is needed.
  • Argument validity: arguments match the schema and the user's intent (IDs, amounts, dates).
  • Least privilege: the agent cannot act beyond the user's permissions, even when instructed to.
  • Human approval: destructive or irreversible actions (delete, pay, send) require confirmation.
  • Failure handling: tool timeouts, errors, and empty results lead to retries with limits or safe escalation.
  • Loops and budgets: step, token, and cost limits stop runaway loops.
  • Side effects: run in a sandbox and assert on the end state (records created, emails queued), plus idempotency on retry.

Multimodal (images, audio, documents)

  • Input variety: low resolution, rotated, cropped, handwritten, scanned PDFs, noisy audio, accents.
  • Extraction accuracy: field-level precision and recall for OCR / document parsing against labeled data.
  • Hidden instructions: text embedded in images or metadata must not be executed as instructions.
  • Generated media safety: no disallowed imagery, likeness misuse, or copyrighted marks where prohibited.
  • Accessibility: generated alt text and transcripts are accurate and useful.
  • Limits: file size, page count, and unsupported formats fail with clear messages.

Evaluation methods

Layer them: cheap automated checks first, expensive human judgment where it matters most.

Evaluation methods with best uses and pitfalls
MethodBest forCost / speedWatch out for
Deterministic assertionsSchemas, length, required keywords, banned terms, PII regex, tool-call argumentsCheap, instantToo strict for free text; only checks surface properties
Reference-based comparisonFacts, calculations, extraction, classificationCheap once references existExact-match is brittle; references go stale
LLM-as-judgeRelevance, tone, faithfulness, rubric scoring at scaleModeratePosition and verbosity bias, self-preference; must be calibrated against humans and version-pinned
Human reviewHigh-risk domains, nuanced safety, grader calibration, final sign-offExpensive, slowInconsistent reviewers — use rubrics, double-label a sample, measure agreement

Writing a good judge rubric

Score one property per prompt; define each score level with a concrete example; ask for a short rationale before the score; prefer pass/fail or pairwise comparison over 1–10 scales; and never let a judge be the only gate for critical-severity risks.

Handling nondeterminism

Do

  • Run each case multiple times (e.g. 5–10) and report pass rate, not a single result.
  • Pin model version, temperature, and seed where the provider supports it; record them with every result.
  • Assert on properties ("mentions refund window", "valid JSON") instead of exact strings.
  • Compare candidate vs. baseline on the same dataset in the same run window.
  • Report sample size and uncertainty; a 2-point change on 50 cases is usually noise.

Avoid

  • Snapshot tests on full model output.
  • Re-running a flaky case until it passes and calling it green.
  • Testing only at temperature 0 when production uses a higher value.
  • Letting average scores hide a failing slice or a single critical failure.
  • Tuning prompts on the same cases used to approve the release.

What to include in a GenAI bug report
  • Exact input, conversation history, attached files, user role, and locale.
  • Model, prompt, and dataset/index versions; temperature and other parameters.
  • Full trace: retrieved chunks, tool calls and arguments, raw model output.
  • Reproduction rate (e.g. "fails 4 of 10 runs") — not just "it happened once".
  • Expected behavior, actual behavior, and the requirement or risk it violates.

Common pitfalls

"It worked in the demo"

A handful of hand-picked prompts says nothing about real users. Require a representative dataset with tagged slices before any go/no-go decision.

Silent provider updates

Model aliases can change behavior without a code change. Pin versions and re-run the suite whenever the provider, model, or prompt changes.

Security by prompt

"Never reveal customer data" in the system prompt is not a control. Enforce permissions in code and test that the model cannot bypass them.

Trusting the judge blindly

An uncalibrated LLM grader can approve confident nonsense. Measure its agreement with human reviewers and re-check it when the grader model changes.
